Skopos deep dive, numbers dated 2026-11-09

How Skopos is built, and how I know it works

Skopos is a free MCAT study app in development for Windows and Mac. AI coding agents wrote its code, under written contracts and tests I set. This page shows the machinery: the harness that checks the agents, the question generator, the scheduler maths, how study data is protected, and the test suite. Every number here comes from my project handbook, which was checked against the code on 2026-11-09, or straight from the code and the plan records.

1. The zero-trust harness

AI coding agents are capable but untrusted. They write real code fast, and they also report a test as passing when it never ran, or fix a different bug than the one asked, with full confidence. So in this harness an agent saying "done, tests pass" counts as a guess until something other than the agent proves it.

  1. ContractWhy, what, the bar for done, the files allowed
  2. Failing testRed on the old code first
  3. BuilderIts own branch and folder
  4. ReceiptWritten by a script, not the agent
  5. Blind verifierTries to break it, HOLDS or FAILS
  6. Done gateRefuses without receipt and verdict
  7. Merge gateReruns tests on the merged code
  8. My own runI use the app at key gates

Follow one real task: VAULT-LEGACY, 2026-11-09

The steps below are the task record in the project plan, quoted where the words matter. Use Next and Back, or pick a step.

  1. Found

    A gap turns up while I write the handbook

    Writing the chapter on architecture, I found that after the move into the encrypted vault, the cleanup removed only two kinds of temporary file. The task record says the cleanup "removes only .pre-sqlcipher- and .backup.json files", so study data could stay on disk unencrypted. A blind verifier confirmed it.

  2. Contract

    The task gets a written contract

    The bar for done, word for word from the plan:

    a new unit or e2e test fails on trunk (plain Skopos_Data.json still present after a migrated boot) and passes after the fix

    The write scope lists five paths: main.js, src/main/storageAdapter.js, tests/unit/ and two project maps. The instruction also fences off one decision: "Do not change sandbox settings (a decision for later, record it)."

  3. Verifier finds more

    The scope widens, on the record

    Before the fix landed, a blind verifier found that the gap was bigger: "up to 5 plain .bak copies held student text after a verified open", and "one safe-mode boot pins json for good". The task was widened by a recorded decision, because "plain student data on disk defeats the encryption".

  4. Failing test

    The test is red before the fix

    tests/unit/vaultLegacyPlainJson.test.js holds four cases. Run against the trunk, three of the four fail, each on plain student text left on disk. That proves the test can see the problem.

  5. Builder

    The fix, on its own branch

    The builder worked on the branch lane/vault-legacy. A new function, removePlainCopies, deletes the plain data file, its old names and every .bak copy, but only while the vault is the verified live store. In safe mode, where the plain file is the data, it touches nothing. A profile stuck in safe mode now tries the vault again on the next boot.

  6. Receipt

    A script records the run

    The receipt .claude/receipts/VAULT-LEGACY.json, in part:

    "label": "VAULT-LEGACY",
"exitCode": 0,
"durationMs": 9228,
"git": { "head": "61214dfae240...", "branch": "lane/vault-legacy" },
"scopeFiles": { "src/main/storageAdapter.js": "3e05f37d145a939a...", ... }

    It stores the real exit code, the commit and a SHA-256 fingerprint of each file in scope. If any of those files changes afterwards, the receipt stops confirming.

  7. Verifier HOLDS

    The blind verifier signs off

    Its one-line verdict, as stored in the plan, opens:

    HOLDS tests/unit/vaultLegacyPlainJson.test.js 4/4 on branch, 3/4 fail on flow-build on plain student text left on disk

    It goes on to record a probe it ran itself: with a wrong key or a corrupt vault the plain files are kept, and with the good key only the encrypted vault is left. The sandbox setting was unchanged, as the contract required, and the receipt confirmed with 60 tests passing.

  8. Merge

    Merged into the trunk

    The branch reached the trunk flow-build in merge commit 27c4773eb. After the merge, the vault test and the save test ran together: 8 tests, 8 passed, 0 failed.

Written contracts

A script generates each contract from the plan. About 163 contract files existed on 2026-11-09. Each one says why the task exists, what to do, the bar for done, the only files the agent may touch, and what is not its call. If the fix needs another file, the agent stops and reports.

Tests built to fail first

The bar names a test that must be red on the old code. A test that passes before and after the change proves nothing. Builders may not edit a failing behaviour test to make it pass. The one exception is a declared golden file rebuild, and then the builder must say which values moved and why.

Isolated branches

Each task runs on a branch named lane/ plus a name, usually in its own worktree folder, so one agent cannot break the tests of another with half-done work. On 2026-11-09 there were about 142 worktrees and about 181 lane branches on GitHub.

The blind verifier

A second agent reads only three things: the diff, the receipt and the bar set for the task. It never reads the reasoning of the builder. It reruns the commands, puts the old code back to check the test goes red, checks no test was weakened, and changes nothing. A FAILS needs evidence, a command that exits non-zero or a file and line. The reply is one line, HOLDS or FAILS.

Receipts, and the day one was faked

A receipt records the command, its real exit code, the counts, the Git commit and a SHA-256 hash of every file in scope, and the check reruns the command. On 2026-10-05 an audit replaced the receipt script with a two-line fake that always printed ok, and a task got marked done. Now the receipt script has its own fingerprint, signed and kept inside the .git folder, and the plan checks it before believing any verdict.

The done gate and the merge gate

state.js done refuses a task without a receipt, without a named verifier, or without a one-line verdict that starts with HOLDS. Then it checks the receipt is signed and still passes. The merge script reruns the unit tests the branch changed on the merged code, rebuilds the app when its source changed, and rechecks the receipt there. If the branch changed a test it did not run, the answer is INCOMPLETE, never GREEN.

The command guard

A small script checks every shell command an agent is about to run. I called it directly on 2026-11-09. Its answers, shortened:

"git add -A"           => refused: stage explicit paths
"git push --force"     => refused: never force-push
"npx playwright test"  => refused: use the repo script, which takes the app lock and rebuilds
"git add scripts/a.js" => allowed

It also has limits I tested the same day. Staging a whole folder by name is allowed. A banned command inside quotes is allowed, because quoted text is treated as data so a commit message cannot trip it. Running Playwright by its file path is allowed. It is a seatbelt for honest mistakes, not a wall against an agent trying to get round it. The receipts and the verifier are the deeper checks.

Real catches, the week of 2026-11-09

  • A count that was one off. I wrote that tests/unit had 1,391 files and 421 receipts were committed. The verifier counted again and got 1,392 and 422, because my own commit had added a test file and a receipt after I counted. Counts became "about", with the date.
  • A clock claim that was backwards. I wrote that the test clock "runs a fixed amount behind" to reach Monday. The verifier pointed at tests/e2e/helpers/pinnedClock.js:4, which says the pin moves the clock ahead, never behind. The receipt was green both times. Only the blind reader caught the words.
  • A cascade nobody enforced. The database schema declares that deleting a deck deletes its notes, but the setting that makes SQLite enforce it is never switched on. Found while the handbook chapter on data was verified. Task SAVE-GAP chose to keep the deletes in code, label the schema clauses "dead by design", and add a test that deleting a deck leaves no orphan rows.
  • A missed network path. My first privacy search looked only for fetch(. The verifier caught calls made through a renamed function, fetchImpl(: the calls that ask each AI provider for its model list. I reran a broader search and read every hit.
  • A test change put on the record. The SAVE-GAP fix made one assertion in an older test untrue: it checked that the old file was gone, and now the old file is kept aside. The change was not made quietly. It was written into the plan as a decision with its reason, and the verifier confirmed that only that one line changed.

Honest limits

Model output is not deterministic. The same prompt can give different code. The gates are deterministic: the same files and the same command give the same verdict, and the same shell command gets the same refusal. Some guards, like the command guard, run as Claude Code hooks, while the rules, the checks, the receipts and the plan are my own scripts. The builder and the verifier are both AI models and can share a blind spot. The merge reruns the changed tests, not the whole suite. There is no CI on every push yet, so a receipt proves a test passed on this one machine. About 54 done tasks are marked "legacy", finished before the verifier rule existed. And my own runs of the app are not yet recorded in the plan.

2. The question generator

Language models write the questions, and other models and code check them. The pipeline is called BWV, for Blueprint, Writer, Verifier. A question that fails any step is dropped with a named reason, and the questions written alongside it carry on. Select a stage to see what it checks and a real case from the records.

Plan, Write, Lint and maths, Solve, Lure, Gates, Grounding, Land. Each stage is shown below.

Plana model

One call plans a batch of blueprints: what each question asserts, the operation, the key claim, the steps, and three real misconceptions to turn into wrong choices. Each blueprint is also told which letter its key goes at, rotating through A to D.

From the BB-R25 run log: "planned 6 · written 10 · lint-failed 1 · solver-verified 4 · grounded 4 · landed 4". Ten drafts gave four questions.

Writea model

One call per blueprint writes the question from a gold example and cites the span of the source that supports the answer. For CARS, the reading section, the writer does not write the passage. CARS passages are real excerpts, word for word, credited to their authors, and the writer gets the passage as fixed text and writes only the questions. Science passages are written from a real source and may invent an experiment, never a fact the source does not state.

Why CARS changed: in a blind rating on 2026-11-01, the rater spotted all 12 model-written CARS passages as purpose-written. As of 2026-11-07, every landed CARS passage is from open-access humanities essays in the Open Library of Humanities and PubMed Central.

Lint and mathscode

Code, not a model, checks each draft: duplicate wrong choices, text the app cannot print, and a numeric answer that does not match its own formula. For a numeric key, the writer must hand over the formula. A small parser computes it, with no eval and only a fixed list of functions and constants. It refuses any number the question never gave, requires the key to match at its own significant figures and sign, and requires that no wrong choice also matches.

The case behind it: a paid judge model caught a wrong key on some reads and missed it on others: "approximately 6.66 m/s" where the square root of 44.28 is 6.654, and +8.82 J where the work is negative. When I ran the check on a test item, "6.65 m/s" failed as key_computation_mismatch, and a formula using 3.1, a number the stem never gave, failed as key_computation_foreign_number.

Solvea second model

A different model answers with the source open, like a strong student. It looks for a second defensible answer, two choices that say the same thing, or a stem that gives the answer away. In strict mode, a solver confidence under 0.75 drops the question.

In the BB-R25 batch: of 10 drafts, 1 failed the lint and 4 were verified by the solver. The rest did not go on.

Lurea small model, recorded

A small, cheap model answers with the book closed, like a novice. Which wrong choice tempts it is recorded on the question. This stage measures and does not reject, except in one catalogue path. Where its answer is used as a gate, it is asked twice with the choices rotated, so its own favourite letter cannot decide.

Real case: this stage drops nothing in the main path, so the records hold measurements, not rejections.

Gatescode, then a judge

Code checks again, then a judge model scores the question against the item standard. A failure is dropped with its reason.

A lesson from the code: the header of the gates file said it was "called by nothing yet". That comment was stale. The pipeline calls it in two places. Trust what the code does, not what a comment says.

Groundingcode, then a verifier

Code looks for the cited quote in the source. An exact match passes. Otherwise at least 80 percent of its words must appear in one window of the source the same length. A verifier model then says whether the line supports the answer: yes passes, partial fails. If the source also supports a wrong choice, the question fails as distractor_supported. In CARS no outside fact is allowed at all.

A threshold set by measurement: for CARS, the content words of the key must match one passage sentence at a share of 0.9 or more. The code records that 0.8 failed a real AAMC question and 0.9 failed none, measured on 53 AAMC CARS items.

Landcode

Only now is the question saved, and only now are its choices rotated by a random amount, with the key and each "why wrong" note moving with their own text. Number choices keep rising order, like the exam. A question whose explanation still names the old letter, such as "The answer is C" after the key moved to A, is dropped as letter_mismatch.

What it gives: across 2,109 landed questions counted on 2026-11-09, the key was A 503 (23.9%), B 573 (27.2%), C 555 (26.3%) and D 478 (22.7%). Close to a quarter each, not exact.

3. The planner and FSRS

The plan is derived, not stored. deriveRoad() is a pure function of the exam date, the minutes a day, the study days and the work already done, so a missed day or a moved exam recomputes the whole plan. Only the choices the student makes, such as a booked day off, are saved. Reviews are scheduled by FSRS through the open-source ts-fsrs library, version 5.3.2, with FSRS-6 and its 21 weights. One module owns it, and it is pure: it takes a card and a grade and returns the new card.

Stability

How many days the memory lasts before the chance of recall falls to 90 percent. A bigger number is a stronger memory.

Difficulty

How hard this card is for this student, from 1 to 10.

Retention target 0.9

The scheduler aims for a 9 in 10 chance of recall on each due date. Skopos keeps the ts-fsrs default, read from the live engine on 2026-11-09, with interval fuzz off, so the same review always gives the same date.

Two schedulers, one parameter set

A flashcard keeps short repeats inside one sitting, so a Good on a new card is back in ten minutes. A question does not, because the Today screen counts what is owed on a calendar day, and a question answered once used to show as due again the same day. The question scheduler is the same scheduler with short-term steps switched off and nothing else changed.

A guard on imported settings

ts-fsrs quietly swaps in its default weights for a vector of the wrong length and never throws. Without a check, the app would say imported Anki settings were active while it ran the defaults. The engine checks the values first and refuses anything out of range by name.

4. Data and encryption

Skopos does not have an account or a server. Study data is one SQLCipher database on the computer it runs on. SQLCipher is SQLite that encrypts the whole file.

The key

A random 32-byte key is made on first run and stored through Electron safeStorage, which hands the job to the protected store of the operating system. If that store is not available, the key manager refuses to work. There is no plain-text fallback. AI provider keys and the phone pairing secret follow the same rule.

The proof

A plain SQLite file always starts with the words SQLite format 3. An end-to-end test boots the real app and fails if the database file starts that way. Opened with the plain SQLite library and no key, a vault made by the test simulation gives one answer: "file is not a database".

If the vault will not open

A boot guard restores the last good copy, runs in a safe mode and tells the student, rather than losing work. While safe mode lasts, the data is plain JSON on disk. That is a real gap, and it is written down.

What leaves the machine

I searched the app code for every network call and read each hit, on 2026-11-09. The list, in order of when it happens:

  1. Every launch: two scripts load from public CDNs, JSZip and MathJax. Nothing in the app uses them. This is an open finding.
  2. 60 seconds after start, packaged builds only: the update check asks GitHub Releases for a new version.
  3. When a student saves an AI key: the app asks that provider (Google, OpenAI, Anthropic or Groq) which models the key can use. That sends the key before any question is made. With no key saved, no call is made.
  4. When the student generates with that key: the prompt goes to the chosen provider, and it can include study text.
  5. When a phone is paired: messages pass through a relay, sealed with AES-256-GCM first, with keys from a secret that travels only in the QR code. The relay cannot open them.
  6. Links: only web links, opened in the system browser.
  7. Crash reports: nothing. Sending needs a yes and a project address, and the address is empty.

Not audited: the code inside installed libraries, and what Electron or the operating system sends by itself. A search finds only what its pattern names, so the next step is a test that fails when a new network call appears.

Fixed this week: plain copies removed

After the move into the vault, the old plain Skopos_Data.json and up to five plain .bak copies stayed beside the encrypted file. Since VAULT-LEGACY, merged on 2026-11-09, they are deleted once the vault opens and verifies, never in safe mode. The walk-through above follows this task.

Fixed this week: a crash-safe save

When Windows refused a rename, one save path deleted the old file before renaming the new one, so a crash in that instant left no data file. Since SAVE-GAP, merged on 2026-11-09, the old file is moved aside and never deleted, the next boot can load it, and the aside copy is removed once a save lands.

Still open: the main window runs with context isolation on and Node integration off, but its sandbox is off. The two PDF helper windows are sandboxed.

5. Testing by the numbers

File counts taken on 2026-11-09 with find. A file holds many test cases.

  • About 1,390Node test files in tests/unit, plus 3 in tests/integration
  • 349React component test files, run by Vitest
  • 228Playwright specs that boot the real Electron app
  • 14golden masters, compared to 10 decimal places

A golden test that can fail

The golden masters hold the full output of the plan and scheduling maths for fixed inputs. One test plants a change of 0.000000001 in a copy and proves the comparison catches it. A master is never rebuilt just to clear a red.

Six months in two minutes

A simulated student studies 180 days through the real save path and a real encrypted database, with Sundays off, a holiday, a three-week gap, a 400-review catch-up and 16 scripted chaos events. With seed 1: zero failures in 2 minutes 12 seconds, six practice exams sat.

Three years, then a wipe

A second simulated student uses the app for 1,095 days, then exports and resets. My run: 23 of 23 checks passed, a 4.8 MB export came back byte for byte with zero records lost. It saves weekly, not daily, to keep the run to five minutes.

100,000 cards

A scale run loads 100,000 cards and 4,000 questions into a 49.7 MB vault. The due scan took 41 ms, and the deck page draws at most 49 rows at any size. One open finding: the Progress activity chart took 600 ms against a 250 ms bound, because it reads all 332,643 raw study events.

Checks that are proven to fail

A 48-day soak runs with a fault planted in the save, which adds one to every review count. The test passes only if the soak goes red. A long green run means nothing until a broken run turns it red.

What is not measured

Skopos does not have code coverage reporting or CI on every push. The end-to-end specs are slow, three at a time. I would add both next.
