Skopos technical deep dive

How Skopos is built and tested

Skopos is a free MCAT study app in development for Windows and Mac. AI coding agents wrote its code and its tests. I wrote the task contracts and the project rules, including the rule that every task needs a test that fails on bad work. This page covers five parts of the project: the harness that checks the agents, the question generator, the planner and FSRS scheduling, data protection, and the test suite. The figures come from my project handbook, which was checked against the code, and from the code and the project plan directly.

1. The zero-trust harness

I treat AI coding agents as capable but untrusted. They write working code quickly, and they can also report a test as passing when it did not run, or fix a different bug from the one requested. In this harness, an agent reporting that a task is done is not accepted until a separate check confirms it.

  1. ContractPurpose, instructions, acceptance test, write scope
  2. Failing-first testFails on the old code
  3. BuilderWorks on its own branch and worktree
  4. ReceiptWritten by a script
  5. Blind verifierReturns HOLDS or FAILS
  6. Done gateRequires a receipt and a verdict
  7. Merge gateReruns tests on the merged code
  8. Owner checkI run the app at key gates

Steps with a blue top edge can reject the work.

Example task: VAULT-LEGACY, 2026-11-09

Each step below is taken from the task record in the project plan and the commit history of its branch. Use Next and Back, or select a step.

  1. Finding

    Plain copies of study data were left on disk

    While the architecture chapter of the handbook was written and checked, a gap was found. After the move into the encrypted vault, the cleanup step deleted only the .pre-sqlcipher- and .backup.json files. The old plain data file stayed on disk. A blind verifier confirmed the finding, and the task was opened from it.

  2. Contract

    The contract set the acceptance test and the write scope

    The acceptance test, as written in the plan:

    a new unit or e2e test fails on trunk (plain Skopos_Data.json still present after a migrated boot) and passes after the fix ...

    The rest of the acceptance text requires the citation checks for the two project maps in tests/unit to stay green. The write scope, as recorded, was src/main/main.js, src/main/storageAdapter.js, tests/unit/ and two project maps. The instruction also excluded one change: "Do not change sandbox settings (a decision for later, record it)."

  3. Fix 1

    The builder added a failing-first test and a first fix

    On the branch lane/vault-legacy, commit 7df4c0abe added tests/unit/vaultLegacyPlainJson.test.js and a first fix. The fix deleted the plain data file after the encrypted vault opened and verified, and left safe mode unchanged.

  4. Review 1

    The verifier returned FAILS and found more plain copies

    The verifier reported that "up to 5 plain .bak copies held student text after a verified open", and that "one safe-mode boot pins json for good". The recorded reason was that "plain student data on disk defeats the encryption".

  5. Scope change

    The task scope was widened by a recorded decision

    Commit 00610833f recorded the decision in the plan. After the vault is verified readable, the plain .bak copies are removed as well. A profile left on JSON by a safe-mode boot returns to the vault on the next healthy boot.

  6. Fix 2

    The second fix moved the cleanup into one function

    Commit 61214dfae added removePlainCopies, which runs only after a verified encrypted open. In safe mode the plain file holds the live data, so the function does not touch it. A profile in safe mode now tries the vault again on the next boot.

  7. Review 2

    The verifier returned FAILS a second time

    The verifier found two problems. Line numbers cited in the project map were out of date after the code moved. On the old code, the tests failed because a function they called did not exist yet. They needed to fail because plain files were left on disk.

  8. Fix 3

    The tests were corrected to fail on the actual defect

    Commit 3ce478ddf changed the tests to call only helpers that exist on the old code. On the trunk, the core cases now fail on plain student text left on disk. The project map cites the correct lines.

  9. Review 3

    The verifier returned HOLDS

    The verdict stored in the plan begins:

    HOLDS tests/unit/vaultLegacyPlainJson.test.js 4/4 on branch, 3/4 fail on flow-build on plain student text left on disk

    The verdict also records a probe the verifier ran. With a wrong key or a corrupt vault, the plain files were kept. With the correct key, only the encrypted vault remained. The sandbox setting was unchanged, as the contract required.

  10. Receipt

    The receipt recorded the test run

    An excerpt from .claude/receipts/VAULT-LEGACY.json:

    "label": "VAULT-LEGACY",
"exitCode": 0,
"durationMs": 9228,
"git": { "branch": "lane/vault-legacy", ... },
"scopeFiles": { "src/main/storageAdapter.js": "3e05f37d145a939a...", ... }

    The receipt stores the exit code, the commit and a SHA-256 hash of each file in scope. If any of those files changes later, the receipt no longer confirms. The verifier recorded the receipt as confirmed, with 60 tests passing.

  11. Merge

    The branch was merged into the trunk

    Merge commit 27c4773eb brought the branch into flow-build. After the merge, the vault test and the save test ran together with 8 tests, 8 passed and 0 failed.

Task contracts

A script generates each contract from the project plan. There are about 175 contract files. Each contract states why the task exists, what to do, the acceptance test, the files the agent may change, and the decisions that are outside its scope. If a fix needs a file outside the write scope, the agent stops and reports it.

Failing-first tests

The acceptance test must fail on the old code before the change and pass after it. This shows the test detects the defect. Builders may not edit a failing behaviour test to make it pass. The one exception is a declared golden file rebuild, where the builder must list which values changed and why.

Branches and worktrees

Each task runs on a branch named lane/ plus a task name, usually in its own Git worktree, so unfinished work in one task does not affect the tests of another. There are about 150 worktrees and about 200 lane branches on GitHub.

The blind verifier

The verifier is a second AI agent. It reads only the diff, the receipt and the acceptance test, and never the reasoning of the builder. It reruns the commands, restores the old code to check that the test fails, checks that no test was weakened, and does not edit anything. A FAILS verdict must cite evidence, either a command that exits non-zero or a file and line. The reply is one line that starts with HOLDS or FAILS.

Receipts

A receipt records the command, its exit code, the pass and fail counts, the Git commit and a SHA-256 hash of every file in scope. The check command rehashes the files and reruns the command. On 2026-10-05 an audit replaced the receipt script with a two-line script that always reported success, and a task was marked done. Since then, the hash of the receipt script is signed and stored inside the .git folder, and the plan script checks it before it accepts any verdict.

The done gate and the merge gate

state.js done rejects a task that has no receipt, no named verifier, or no one-line verdict starting with HOLDS. It then checks that the receipt is signed and still passes. The merge script reruns the unit tests the branch changed on the merged code, rebuilds the app when its source changed, and checks the receipt again. If the branch changed a test that was not run, the result is INCOMPLETE.

The command guard

A script checks each shell command before an agent runs it. These are its responses, shortened:

"git add -A"           => refused: stage explicit paths
"git push --force"     => refused: never force-push
"npx playwright test"  => refused: use the repo script, which takes the app lock and rebuilds
"git add scripts/a.js" => allowed

I also tested its limits. Staging a whole folder by name is allowed. A banned command inside quotes is allowed, because the guard treats quoted text as data so that commit messages do not trigger it. Running Playwright by its file path is allowed. The guard prevents accidental mistakes. It does not stop an agent that deliberately works around it, so the receipts and the verifier remain the main checks.

Defects the harness caught

  • A test file count was off by one. A handbook draft stated 1,391 files in tests/unit and 421 committed receipts. The verifier counted 1,392 and 422, because the commit for the draft had added a test file and a receipt after the count. Counts are now given as approximate, with the date.
  • A statement about the test clock was reversed. A draft stated that the test clock "runs a fixed amount behind" to reach Monday. The verifier cited tests/e2e/helpers/pinnedClock.js:4, which states that the clock moves ahead and never behind. The verifier found the error by reading the source of the clock helper. In this case and the count case above, the receipts were green because the tests passed. Only the blind review found the errors in the text.
  • A cascade delete was declared but not enforced. The database schema declares that deleting a deck deletes its notes, but the SQLite setting that enforces foreign keys is never switched on. This was found while the data chapter of the handbook was verified. Task SAVE-GAP kept the deletes in code, labelled the schema clauses "dead by design", and added a test that deleting a deck leaves no orphan rows.
  • The privacy audit missed one network path. The first search looked only for fetch(. The verifier found calls made through a renamed function, fetchImpl(, which request the model list from each AI provider. The search was widened and every result was reviewed.
  • One test assertion was changed through a recorded decision. After the SAVE-GAP fix, an older test still checked that the old data file was deleted, while the fix now keeps it aside. The change to that assertion was recorded in the plan as a decision with its reason, and the verifier confirmed that only that line changed.
  • A spec assertion was changed only after my approval. An end-to-end test limited exam charts to half the pane width, while the design board and my ruling of 2026-11-08 set charts to the full width of the passage column. The builder found that the test was out of date and did not change the assertion without approval. I approved the change on 2026-11-09, and the approval is recorded in the plan under task EXHIBIT-WIDTH.
  • The new locked-vault screen could have shown the wrong message. For task KEY-LOST, the verifier found that an older menu line stating the data was not encrypted still appeared while the vault was locked. It also found that a corrupt vault would have been reported as a missing key. The recovery screen now appears only when the key is missing or unreadable, and the older line is hidden while the vault is locked.

Limits of the harness

Model output is not deterministic, and the same prompt can produce different code. The scripted gates, which are the tests, the receipts, the command guard and state.js done, give the same result every time for the same input. The blind verifier is a second AI model. It is blind and adversarial, and any defect it reports must be shown by a failing test before the code changes. The command guard and some other guards run as Claude Code hooks. The rules, checks, receipts and plan are scripts in the project itself. The builder and the verifier are both AI models and can miss the same problem. The merge gate reruns the changed tests, not the full suite. There is no continuous integration on every push yet, so a receipt shows that a test passed on this one machine. About 54 completed tasks are marked "legacy" because they were finished before the verifier rule existed. My own runs of the app are not yet recorded in the plan.

2. The question generator

Language models write the questions, and other models and code check them. The pipeline is called BWV, for Blueprint, Writer, Verifier. A question that fails any stage is dropped with a named reason, and the other questions in the batch continue. Select a stage to see what it checks and an example from the project records.

The stages in order are Plan, Write, Lint and maths, Solve, Lure, Gates, Grounding and Land. Each stage is described below.

Planmodel

One call plans a batch of blueprints. Each blueprint sets what the question asserts, the operation, the key claim, the steps, and three common misconceptions to use as wrong choices. Each blueprint is also assigned the letter for its key, rotating through A to D.

The BB-R25 run log records one batch as "planned 6 · written 10 · lint-failed 1 · solver-verified 4 · grounded 4 · landed 4", so ten drafts produced four landed questions.

Writemodel

One call per blueprint writes the question from a gold example and cites the span of the source that supports the answer. The writer does not write CARS passages. CARS passages are real excerpts, word for word, credited to their authors, and the writer receives the passage as fixed text and writes only the questions. Science passages are written from a real source. They may describe an invented experiment, but they may not state a fact the source does not support.

CARS passages were changed to real excerpts after a blind rating on 2026-11-01, in which the rater identified all 12 model-written passages as purpose-written. Every landed CARS passage so far comes from open-access humanities essays in the Open Library of Humanities and PubMed Central.

Lint and mathscode

Code checks each draft for duplicate wrong choices, text the app cannot display, and numeric answers that do not match their formula. For a numeric key, the writer must supply the formula. A small parser evaluates it without eval, using a fixed list of functions and constants. The check rejects any number the question does not give, requires the key to match the computed value at its own significant figures and sign, and requires that no wrong choice also matches.

This check was added because a paid judge model detected a wrong key on some runs and missed it on others. One key read "approximately 6.66 m/s" where the square root of 44.28 is 6.654. Another gave +8.82 J where the work is negative. On a test item, "6.65 m/s" failed as key_computation_mismatch, and a formula that used 3.1, a number the stem does not give, failed as key_computation_foreign_number.

Solvesecond model

A different model answers the question with the source available. It checks for a second defensible answer, two choices that mean the same thing, or a stem that reveals the answer. In strict mode, a solver confidence below 0.75 drops the question.

In the BB-R25 batch, 10 drafts were written, 1 failed the lint stage and 4 were verified by the solver. The other drafts did not continue.

Luresmall model, measurement only

A small model answers without the source, to estimate how a less prepared student would answer. The wrong choice it selects is recorded on the question. This stage does not reject questions, except in one catalogue path. Where its answer is used as a gate, it answers twice with the choices rotated, so that its preferred letter does not affect the result.

Gatescode, then judge model

Code runs a second set of checks, then a judge model scores the question against the item standard. A question that fails is dropped with its reason.

The header comment of the gates file stated that the file was "called by nothing yet". The comment was out of date. The pipeline calls the file in two places.

Groundingcode, then verifier model

Code searches the source for the cited quote. An exact match passes. Otherwise, at least 80 percent of the words of the quote must appear within one window of the source of the same length. A verifier model then rates whether the line supports the answer. Only a full yes passes. If the source also supports a wrong choice, the question fails as distractor_supported. CARS questions may not rely on any fact outside the passage.

For CARS, the content words of the key must match one passage sentence at a share of 0.9 or higher. The code records that a threshold of 0.8 failed one real AAMC question and 0.9 failed none, measured on 53 AAMC CARS items.

Landcode

The question is saved only at this stage, and its choices are then rotated by a random amount. The key and each "why wrong" note move with their own text. Numeric choices stay in ascending order, as on the exam. A question whose explanation still names the old letter, such as "The answer is C" after the key moved to A, is dropped as letter_mismatch.

In a count of 2,109 landed questions, the key was A for 503 (23.9%), B for 573 (27.2%), C for 555 (26.3%) and D for 478 (22.7%).

3. The planner and FSRS

The study plan is calculated each time and is not stored. deriveRoad() is a pure function of the exam date, the daily study minutes, the study days and the work already completed. A missed day or a new exam date recalculates the whole plan. Only the choices the student makes, such as a booked day off, are saved. Reviews are scheduled by FSRS through the open-source ts-fsrs library, version 5.3.2, which implements FSRS-6 with 21 weights. One module owns the scheduler. It is pure, meaning it takes a card and a grade and returns the updated card without saving anything.

Stability

The number of days until the probability of recall falls to 90 percent. A higher value means a stronger memory.

Difficulty

How hard the card is for this student, on a scale of 1 to 10.

Retention target of 0.9

The scheduler sets each interval so that the probability of recall on the due date is 90 percent. Skopos uses the ts-fsrs default, confirmed from the running engine. Interval fuzz is off, so the same review always produces the same date.

The explorer follows a new practice question that is reviewed on each due date. All values were computed in advance by the app scheduler, src/main/fsrsEngine.js, with its question settings and default parameters. The page only displays them.

To undo a flashcard grade, the app reads the previous state of the card from the review log that ts-fsrs saved with that grade, checks it against a copy taken before the grade, and saves the restored card.

Separate schedulers for cards and questions

A flashcard uses short-term learning steps, so a new card graded Good returns in ten minutes within the same session. A question does not use them, because the Today screen counts work by calendar day, and a question answered once was being counted as due again the same day. The question scheduler is the same scheduler with short-term steps switched off. All other parameters are shared.

Validation of imported settings

When ts-fsrs receives a weight vector of the wrong length, it uses its default weights without raising an error. Without validation, the app would report imported Anki settings as active while it used the defaults. The engine validates the values first and rejects anything out of range by name.

4. Data and encryption

Skopos does not use an account or a server. Study data is stored in one SQLCipher database on the local computer. SQLCipher is a version of SQLite that encrypts the whole database file.

Key storage

A random 32-byte key is generated on first run and stored through Electron safeStorage, which uses the protected storage of the operating system. If that storage is unavailable, the key manager refuses to run. There is no plain-text fallback. AI provider keys and the phone pairing secret are stored the same way.

How encryption is tested

A plain SQLite file always begins with the bytes SQLite format 3. An end-to-end test starts the real app and fails if the database file begins with them. When a vault created by the test simulation is opened with the plain SQLite library and no key, the library returns "file is not a database".

When the vault cannot open

A boot guard restores the last good copy, runs the app in safe mode and informs the student, so no work is lost. In safe mode the data is stored as plain JSON on disk. This is a known gap and is documented.

Network connections

The app code was searched for every network call, and each result was reviewed. The connections, in the order they occur:

  1. On every launch, two scripts load from public CDNs, JSZip and MathJax. The app does not use them. This is an open finding.
  2. Sixty seconds after start, in packaged builds only, the update check asks GitHub Releases for a newer version.
  3. When a student saves an AI key, the app asks that provider (Google, OpenAI, Anthropic or Groq) for the list of models the key can use. This sends the key before any question is generated. With no key saved, no call is made.
  4. When the student generates questions with that key, the prompt is sent to the chosen provider and can include study text.
  5. When a phone is paired, messages pass through a relay. They are encrypted with AES-256-GCM before they leave, using keys derived from a secret that is shared only through the QR code. The relay cannot decrypt them.
  6. Only web links are opened, and they open in the system browser.
  7. Crash reports are not sent. Sending requires the student to opt in and a configured project address, and the address is empty.

The audit did not cover the code inside installed libraries, or traffic that Electron or the operating system sends on its own. A text search finds only what its pattern matches, so the next step is a test that fails when a new network call is added.

Fix: plain copies removed after migration

After the move into the vault, the old plain Skopos_Data.json and up to five plain .bak copies remained beside the encrypted file. Since VAULT-LEGACY was merged, they are deleted once the vault opens and verifies, and never in safe mode. This is the task shown in the example above.

Fix: crash-safe save

When Windows refused a rename, one save path deleted the old file before it renamed the new one, so a crash at that point left no data file. Since SAVE-GAP was merged, the old file is moved aside and kept, the next boot can load it, and the aside copy is removed after the next successful save.

Fix: locked-vault recovery screen

When the key file was lost but the vault remained, the app showed an empty main area with no message. Now a vault that cannot be opened is never deleted or replaced. The student sees a recovery screen titled "Your study data is locked", worded as I approved it, with two buttons, "Restore a backup" and "Copy details".

Open item: the main window runs with context isolation on and Node integration off, but with the sandbox off. The two PDF helper windows run sandboxed.

5. The test suite

Skopos has nearly 2,000 automated test files, and each file contains several test cases.

  • Nearly 2,000automated test files in total
  • About 1,400of them are Node unit and integration test files
  • About 350of them are React component test files, run by Vitest
  • Over 200of them are Playwright end-to-end specs that start the real Electron app

Golden masters

The 14 golden masters store the full output of the planning and scheduling calculations for fixed inputs. One test changes a copy by 0.000000001 and confirms that the comparison detects it. Values are compared to 10 decimal places. A master is rebuilt only when the calculation is changed on purpose, never to clear a failure.

Six-month simulation

A simulated student studies for 180 days through the real save path and a real encrypted database. The schedule includes Sundays off, a holiday, a three-week gap, a 400-review catch-up day and 16 scripted fault events. The run with seed 1 finished in 2 minutes 12 seconds with zero failures and six practice exams.

Three-year simulation

A second simulated student uses the app for 1,095 days, then exports the data and resets the app. In one run, 23 of 23 checks passed and a 4.8 MB export was read back byte for byte with zero records lost. This run saves weekly instead of daily, which keeps it to five minutes.

Scale test with 100,000 cards

A scale run loads 100,000 cards and 4,000 questions into a 49.7 MB vault. The due scan took 41 ms, and the deck page renders at most 49 rows at any deck size. One finding is open. The Progress activity chart took 600 ms against a 250 ms limit, because it reads all 332,643 raw study events.

Fault injection

A 48-day simulation runs with a fault added to the save step, which increments every review count. The test passes only if the simulation reports the failure. This confirms that the check detects a double count.

Not yet in place

Skopos does not have code coverage reporting or continuous integration on every push. The end-to-end specs are slow and run three at a time.
