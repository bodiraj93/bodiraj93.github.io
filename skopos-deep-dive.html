Skopos technical deep dive

How I designed Skopos and how I check it

Skopos is a free MCAT study app in development for Windows and Mac. AI coding agents wrote its code and its tests under the task contracts and project rules that I wrote. The central rule is that a task counts as done only when a test that fails on bad work passes on the new code. This page explains five parts of the design. For each part I describe the problem, the decision I made, the reason for it and the evidence that it works. The numbers come from the project plan, the commit history and the code.

Back to the case study

1. The zero-trust harness

AI coding agents write working code quickly. They can also report a test as passing when it did not run, or fix a different bug from the one they were given. I decided to treat them as capable but untrusted. When an agent reports that a task is done, I accept it only after a check that the agent cannot change confirms it. Every task moves through the steps below, and five of them can reject the work.

  1. ContractPurpose, instructions, acceptance test, write scope
  2. Failing-first testFails on the old code
  3. BuilderWorks on its own branch and worktree
  4. ReceiptWritten by a script
  5. Blind verifierReturns HOLDS or FAILS
  6. Done gateRequires a receipt and a verdict
  7. Merge gateReruns tests on the merged code
  8. Owner checkI run the app at key gates

Steps with a blue top edge can reject the work.

One real task, step by step: VAULT-LEGACY, 2026-11-09

I chose this task because the verifier rejected the work twice before it passed. Each step is taken from the task record in the project plan and the commit history of its branch. Use Next and Back, or select a step.

  1. Origin

    The task came from a handbook check

    I keep a handbook that explains each part of the app, and a blind verifier checks every chapter against the code. During the check of the architecture chapter, the verifier showed that the cleanup after the move into the encrypted vault deleted only the .pre-sqlcipher- and .backup.json files. The old plain data file stayed on disk. The task was opened from that check the same day.

  2. Contract

    The contract set the acceptance test and the write scope

    The acceptance test, as written in the plan, reads as follows.

    a new unit or e2e test fails on trunk (plain Skopos_Data.json still present after a migrated boot) and passes after the fix ...

    The rest of the acceptance text requires the citation checks for the two project maps in tests/unit to stay green. The write scope, as recorded, was src/main/main.js, src/main/storageAdapter.js, tests/unit/ and two project maps. The instruction also kept one change out of the task with the words "Do not change sandbox settings (a decision for later, record it)."

  3. Fix 1

    The builder added a failing-first test and a first fix

    On the branch lane/vault-legacy, commit 7df4c0abe added tests/unit/vaultLegacyPlainJson.test.js and a first fix. The fix deleted the plain data file after the encrypted vault opened and verified, and left safe mode unchanged.

  4. Review 1

    The verifier returned FAILS and found more plain copies

    The verifier reported that "up to 5 plain .bak copies held student text after a verified open", and that "one safe-mode boot pins json for good". The recorded reason was that "plain student data on disk defeats the encryption".

  5. Scope change

    The task scope was widened by a recorded decision

    Commit 00610833f recorded the decision in the plan. After the vault is verified readable, the plain .bak copies are removed as well. A profile left on JSON by a safe-mode boot returns to the vault on the next healthy boot.

  6. Fix 2

    The second fix moved the cleanup into one function

    Commit 61214dfae added removePlainCopies, which runs only after a verified encrypted open. In safe mode the plain file holds the live data, so the function does not touch it. A profile in safe mode now tries the vault again on the next boot.

  7. Review 2

    The verifier returned FAILS a second time

    The verifier found two problems. Line numbers cited in the project map were out of date after the code moved. On the old code, the tests failed because a function they called did not exist yet. They needed to fail because plain files were left on disk.

  8. Fix 3

    The tests were corrected to fail for the right reason

    Commit 3ce478ddf changed the tests to call only helpers that exist on the old code. On the trunk, the core cases now fail on plain student text left on disk. The project map cites the correct lines.

  9. Review 3

    The verifier returned HOLDS

    The verdict stored in the plan begins with this line.

    HOLDS tests/unit/vaultLegacyPlainJson.test.js 4/4 on branch, 3/4 fail on flow-build on plain student text left on disk

    The verdict also records a probe the verifier ran. With a wrong key or a corrupt vault, the plain files were kept. With the correct key, only the encrypted vault remained. The sandbox setting was unchanged, as the contract required.

  10. Receipt

    The receipt recorded the test run

    This is an excerpt from .claude/receipts/VAULT-LEGACY.json.

    "label": "VAULT-LEGACY",
"exitCode": 0,
"durationMs": 9228,
"git": { "branch": "lane/vault-legacy", ... },
"scopeFiles": { "src/main/storageAdapter.js": "3e05f37d145a939a...", ... }

    The receipt stores the exit code, the commit and a SHA-256 hash of each file in scope. If any of those files changes later, the receipt no longer confirms. The verifier recorded the receipt as confirmed, with 60 tests passing.

  11. Merge

    The branch was merged into the trunk

    Merge commit 27c4773eb brought the branch into flow-build. The vault test then stayed in use as a regression check. The receipt for a later task, KEY-LOST, ran it together with the locked-vault test, and 8 of 8 tests passed.

Task contracts

A script generates each contract from the project plan, and there are about 175 contract files. Each contract states why the task exists, what to do, the acceptance test, the files the agent may change, and the decisions that are outside its scope. I limit the write scope because an agent that may change any file can make a test pass by changing the wrong one. If a fix needs a file outside the scope, the agent stops and reports it.

Failing-first tests

The acceptance test must fail on the old code before the change and pass after it. I require this because a test that already passes on the old code says nothing about the fix. Builders may not edit a failing behaviour test to make it pass. The one exception is a declared golden file rebuild, where the builder must list which values changed and why.

Branches and worktrees

Each task runs on a branch named lane/ plus a task name, usually in its own Git worktree, so unfinished work in one task does not affect the tests of another. There are about 150 worktrees and about 200 lane branches on GitHub.

The blind verifier

The verifier is a second AI agent. It reads only the diff, the receipt and the acceptance test, and never the reasoning of the builder, so it judges the result without taking on the builder's assumptions. It reruns the commands, restores the old code to check that the test fails, checks that no test was weakened, and does not edit anything. A FAILS verdict must cite evidence, either a command that exits non-zero or a file and line. The reply is one line that starts with HOLDS or FAILS.

Receipts

A receipt records the command, its exit code, the pass and fail counts, the Git commit and a SHA-256 hash of every file in scope. The check command rehashes the files and reruns the command. On 2026-10-05 an audit replaced the receipt script with a two-line script that always reported success, and a task was marked done. That path was then closed. The hash of the receipt script is now signed and stored inside the .git folder, and the plan script checks it before it accepts any verdict.

The done gate and the merge gate

state.js done rejects a task that has no receipt, no named verifier, or no one-line verdict starting with HOLDS. It then checks that the receipt is signed and still passes. The merge script reruns the unit tests the branch changed on the merged code, rebuilds the app when its source changed, and checks the receipt again. If the branch changed a test that was not run, the result is INCOMPLETE.

The command guard

A script checks each shell command before an agent runs it. These are its responses, shortened.

"git add -A"           => refused: stage explicit paths
"git push --force"     => refused: never force-push
"npx playwright test"  => refused: use the repo script, which takes the app lock and rebuilds
"git add scripts/a.js" => allowed

The guard is meant to stop accidents, and its limits were also tested. Staging a whole folder by name is allowed. A banned command inside quotes is allowed, because the guard treats quoted text as data so that commit messages do not trigger it. Running Playwright by its file path is allowed. An agent that deliberately works around the guard can get past it, so the receipts and the blind verifier are the checks that decide.

Cases the blind review caught

A receipt proves that a command ran and passed. It cannot show that a test checks the right behaviour, or that a sentence in the documentation is true. These cases from the project record are the reason the verifier stays in every task.

  • The recovery screen for a locked vault. For task KEY-LOST, the verifier showed that an older menu line stating the data was not encrypted still appeared while the vault was locked, and that a corrupt vault would have been reported as a missing key. Before the merge, the recovery screen was limited to a missing or unreadable key, and the older line was hidden while the vault is locked.
  • A statement about the test clock. A handbook draft stated that the test clock "runs a fixed amount behind" to reach Monday. The verifier cited tests/e2e/helpers/pinnedClock.js:4, which states that the clock moves ahead and never behind. The receipts were green because the tests passed. Only the blind review found the error in the text.
  • The search for network calls. The first search looked only for fetch(. The verifier found calls made through a renamed function, fetchImpl(, which request the model list from each AI provider. The search was widened and every result was reviewed.
  • A test assertion that disagreed with the design. An end-to-end test limited exam charts to half the pane width, while the design board and my ruling of 2026-11-08 set charts to the full width of the passage column. The builder stopped and did not change the assertion without approval. I approved the change on 2026-11-09, and the approval is recorded in the plan under task EXHIBIT-WIDTH.
  • A changed assertion kept to one line. After the crash-safe save change, an older test still checked that the old data file was deleted, while the new code keeps it aside. The change to that assertion was recorded in the plan as a decision with its reason, and the verifier confirmed that only that line changed.

How I weigh the checks

Model output is not deterministic, and the same prompt can produce different code. For that reason the checks that decide are scripts. The tests, the receipts, the command guard and state.js done give the same result every time for the same input. The verifier is also an AI model, so a defect it reports counts only when a failing test shows it before the code changes. The builder and the verifier can miss the same problem, and that is why I run the app myself at key gates. About 54 tasks were finished before I added the verifier rule. The plan marks them as legacy, so they stay separate from the tasks a blind verifier passed.

2. The question generator

A language model can write a question that reads well and still has a wrong key or a second defensible answer. I decided that models write the questions and separate checks decide whether each one is kept. Some checks are code and some are other models. The pipeline is called BWV, for Blueprint, Writer, Verifier. A question that fails any stage is dropped with a named reason, and the other questions in the batch continue. Select a stage to see what it checks and an example from the project records.

The stages in order are Plan, Write, Lint and maths, Solve, Lure, Gates, Grounding and Land. Each stage is described below.

Planmodel

One call plans a batch of blueprints. Each blueprint sets what the question asserts, the operation, the key claim, the steps, and three common misconceptions to use as wrong choices. Each blueprint is also assigned the letter for its key, rotating through A to D.

The BB-R25 run log records one batch as "planned 6 · written 10 · lint-failed 1 · solver-verified 4 · grounded 4 · landed 4", so ten drafts produced four landed questions.

Writemodel

One call per blueprint writes the question from a gold example and cites the span of the source that supports the answer. The writer does not write CARS passages. CARS passages are real excerpts, word for word, credited to their authors, and the writer receives the passage as fixed text and writes only the questions. Science passages are written from a real source. They may describe an invented experiment, but they may not state a fact the source does not support.

CARS passages became real excerpts after a blind rating on 2026-11-01, in which the rater identified all 12 model-written passages as purpose-written. A real excerpt removes that signal. Every landed CARS passage so far comes from open-access humanities essays in the Open Library of Humanities and PubMed Central.

Lint and mathscode

Code checks each draft for duplicate wrong choices, text the app cannot display, and numeric answers that do not match their formula. For a numeric key, the writer must supply the formula. A small parser evaluates it without eval, using a fixed list of functions and constants. The check rejects any number the question does not give, requires the key to match the computed value at its own significant figures and sign, and requires that no wrong choice also matches.

This check is code because a paid judge model detected a wrong key on some runs and missed it on others. Code gives the same answer every time. One key read "approximately 6.66 m/s" where the square root of 44.28 is 6.654. Another gave +8.82 J where the work is negative. On a test item, "6.65 m/s" failed as key_computation_mismatch, and a formula that used 3.1, a number the stem does not give, failed as key_computation_foreign_number.

Solvesecond model

A different model answers the question with the source available. It checks for a second defensible answer, two choices that mean the same thing, or a stem that reveals the answer. In strict mode, a solver confidence below 0.75 drops the question.

In the BB-R25 batch, 10 drafts were written, 1 failed the lint stage and 4 were verified by the solver. The other drafts did not continue.

Luresmall model, measurement only

A small model answers without the source, to estimate how a less prepared student would answer. The wrong choice it selects is recorded on the question. This stage does not reject questions, except in one catalogue path. Where its answer is used as a gate, it answers twice with the choices rotated, so that its preferred letter does not affect the result.

Gatescode, then judge model

Code runs a second set of checks, then a judge model scores the question against the item standard. A question that fails is dropped with its reason.

Groundingcode, then verifier model

Code searches the source for the cited quote. An exact match passes. Otherwise, at least 80 percent of the words of the quote must appear within one window of the source of the same length. A verifier model then rates whether the line supports the answer. Only a full yes passes. If the source also supports a wrong choice, the question fails as distractor_supported. CARS questions may not rely on any fact outside the passage.

For CARS, the content words of the key must match one passage sentence at a share of 0.9 or higher. The code records that a threshold of 0.8 failed one real AAMC question and 0.9 failed none, measured on 53 AAMC CARS items.

Landcode

The question is saved only at this stage, and its choices are then rotated by a random amount. The key and each "why wrong" note move with their own text. Numeric choices stay in ascending order, as on the exam. A question whose explanation still names the old letter, such as "The answer is C" after the key moved to A, is dropped as letter_mismatch.

In a count of 2,109 landed questions, the key was A for 503 (23.9%), B for 573 (27.2%), C for 555 (26.3%) and D for 478 (22.7%).

3. The planner and FSRS

A study plan has to stay correct after a missed day or a new exam date. I decided the plan is calculated each time and never stored. deriveRoad() is a pure function of the exam date, the daily study minutes, the study days and the work already completed. A missed day or a new exam date recalculates the whole plan, so the plan always matches the work the student has done. Only the choices the student makes, such as a booked day off, are saved. Reviews are scheduled by FSRS, the open scheduler that Anki also offers, through the open-source ts-fsrs library, version 5.3.2, which implements FSRS-6 with 21 weights. One module owns the scheduler. It is pure, meaning it takes a card and a grade and returns the updated card without saving anything, so every interval can be tested with fixed inputs.

Stability

The number of days until the probability of recall falls to 90 percent. A higher value means a stronger memory.

Difficulty

How hard the card is for this student, on a scale of 1 to 10.

Retention target of 0.9

The scheduler sets each interval so that the probability of recall on the due date is 90 percent. Skopos uses the ts-fsrs default, confirmed from the running engine. Interval fuzz is off, so the same review always produces the same date and a test can check it exactly.

To undo a flashcard grade, the app reads the previous state of the card from the review log that ts-fsrs saved with that grade, checks it against a copy taken before the grade, and saves the restored card.

Separate schedulers for cards and questions

A flashcard uses short-term learning steps, so a new card graded Good returns in ten minutes within the same session. A question does not use them. The Today screen counts work by calendar day, and with learning steps a question answered once was counted as due again the same day. The question scheduler is the same scheduler with short-term steps switched off. All other parameters are shared.

Validation of imported settings

When ts-fsrs receives a weight vector of the wrong length, it uses its default weights without raising an error. Without validation, the app would report imported Anki settings as active while it used the defaults. The engine therefore validates the values first and rejects anything out of range by name.

4. Data and encryption

A student's study history is personal. I decided Skopos has no account and no server, and that study data stays on the student's own computer. It is stored in one SQLCipher database. SQLCipher is a version of SQLite that encrypts the whole database file.

Key storage

A random 32-byte key is generated on first run and stored through Electron safeStorage, which uses the protected storage of the operating system. If that storage is unavailable, the key manager refuses to run. There is no plain-text fallback, because a key saved in plain text beside the database would undo the encryption. AI provider keys and the phone pairing secret are stored the same way.

How encryption is tested

A plain SQLite file always begins with the bytes SQLite format 3. An end-to-end test starts the real app and fails if the database file begins with them. When a vault created by the test simulation is opened with the plain SQLite library and no key, the library returns "file is not a database".

When the vault cannot open

A boot guard restores the last good copy, opens the app in safe mode and tells the student. In safe mode the app keeps working from a local JSON copy, so a student never loses a session. The next healthy start moves the data back into the encrypted vault.

Plain copies removed once the vault is verified

After the move into the vault, the old plain Skopos_Data.json and its plain .bak copies are deleted once the vault opens and verifies. They are never deleted in safe mode, because there they hold the live data. This is the task shown in the walk-through above.

A save that always leaves a data file

Windows can refuse a rename. In that case the save moves the old file aside and keeps it, so a crash at any point leaves a data file that the next start can load. The aside copy is removed after the next successful save. A unit test simulates a crash at that point and checks the next start.

A locked vault is never deleted

If the key file is lost and the vault remains, the app never deletes or replaces the vault. The student sees a recovery screen titled "Your study data is locked", in words I approved, with two buttons, "Restore a backup" and "Copy details".

Deletes handled in code

The database schema declares that deleting a deck deletes its notes, and SQLite enforces that only when foreign keys are switched on. The app does not switch them on, so the deletes are done in code, the schema clauses are labelled "dead by design", and a test checks that deleting a deck leaves no orphan rows.

Network connections

Skopos is built to work offline, so every connection it makes has a stated reason. The app loads no script from the internet. Math is typeset by KaTeX from the app's own files, and a unit test fails if index.html gains a script from a web address. The app code was searched for every network call, and each result was reviewed. These are the connections, in the order they occur.

  1. Sixty seconds after start, in packaged builds only, the update check asks GitHub Releases for a newer version.
  2. When a student saves an AI key, the app asks that provider (Google, OpenAI, Anthropic or Groq) for the list of models the key can use, so that it uses the newest model the key offers. This sends the key before any question is generated. With no key saved, no call is made.
  3. When the student generates questions with that key, the prompt is sent to the chosen provider and can include study text.
  4. When a phone is paired, messages pass through a relay. They are encrypted with AES-256-GCM before they leave, using keys derived from a secret that is shared only through the QR code. The relay cannot decrypt them.
  5. Only web links are opened, and they open in the system browser.
  6. Crash reports stay off unless the student opts in, because the data belongs to the student. The reporter is built to scrub every report and to leave out native crash dumps, because raw process memory can hold study text.

5. The test suite

Many faults in a study app appear only after weeks of use, such as a rounding error in the scheduler or a save that loses a day of reviews. I decided the suite would include long simulations and exact golden masters as well as ordinary unit tests. Skopos has nearly 2,000 automated test files, and each file contains several test cases.

  • Nearly 2,000automated test files in total
  • About 1,400of them are Node unit and integration test files
  • About 350of them are React component test files, run by Vitest
  • Over 200of them are Playwright end-to-end specs that start the real Electron app

Golden masters

The 14 golden masters store the full output of the planning and scheduling calculations for fixed inputs. One test changes a copy by 0.000000001 and confirms that the comparison detects it. Values are compared to 10 decimal places. A master is rebuilt only when the calculation is changed on purpose, never to clear a failure.

Six-month simulation

A simulated student studies for 180 days through the real save path and a real encrypted database. The schedule includes Sundays off, a holiday, a three-week break, a 400-review catch-up day and 16 scripted fault events. The run with seed 1 finished in 2 minutes 12 seconds with zero failures and six practice exams.

Three-year simulation

A second simulated student uses the app for 1,095 days, then exports the data and resets the app. In one run, 23 of 23 checks passed and a 4.8 MB export was read back byte for byte with zero records lost. This run saves weekly instead of daily, which keeps it to five minutes.

Scale test with 100,000 cards

A scale run loads 100,000 cards and 4,000 questions into a 49.7 MB vault. The due scan took 41 ms, and the deck page renders at most 49 rows at any deck size. The run also holds the Progress activity chart to 250 ms. It took 600 ms because it reads all 332,643 raw study events to draw 28 days, and the run reports that as a finding.

Fault injection

A 48-day simulation runs with a fault added to the save step, which increments every review count. The test passes only if the simulation reports the failure. This confirms that the check detects a double count.

Where the tests run

I run the tests on my own machine. Before any merge, the merge script reruns the tests the branch changed on the merged tree. The end-to-end specs start the real Electron app and run three at a time.

The Node unit tests and the React component tests also run on GitHub after every push to the main development branch, on a clean Linux machine. Each run reports code coverage: about 83% of Node lines and about 26% of React lines. The React figure is lower because I prove most screen behaviour with the end-to-end specs, which run on my machine and are not counted in it. A few test files need data from my machine or the target hardware. Each one is listed with its reason and still runs on my machine before any merge.
