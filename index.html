Skopos is a free MCAT preparation suite that I am building and leading

It began as a personal flashcard tool and has grown into a complete study platform: a daily plan built around the exam date, questions in the AAMC format with detailed explanations, and spaced-repetition flashcards. I lead the product and test every release. AI coding agents write the code inside a zero-trust test harness I designed, and a change does not ship until it passes.

  • 4.87 / 5explanation quality in a blind AI review, against 4.10 for UWorld
  • 4.60 / 5flashcard accuracy, against 3.92 for the MileDown deck
  • Nearly 2,000automated test files
  • FreeDoes not require an account. Works offline, and study data stays on the student's computer.

The problem

Quality MCAT preparation costs thousands of dollars, and that cost should not decide who gets into medicine. Students trust the official AAMC questions but find the explanations thin. UWorld explains well, but many students cannot afford it. This app offers both, for free.

What it does

Plans every day

Builds a day-by-day schedule from the exam date and the time available, with catch-up and rest days. Anki schedules cards. This plans the whole day: reviews, reading, questions and practice exams.

Exam-format questions

Passage-based questions in the AAMC format. Each wrong answer is explained step by step.

Spaced-repetition flashcards

Each card returns just before it would be forgotten. Anki decks import and export.

Sourced content

Science content comes from OpenStax textbooks. Reading passages are verbatim excerpts from published works.

Question generator

Writes new questions from textbook sections. Several independent checks review each one, and any of them can reject it.

Private by design

Runs locally with encrypted storage. Data does not leave the computer unless the student turns that on.

Engineering decisionsLocal and encrypted storage, the React migration, single owners, headless logic and state.

Local, encrypted storage

Skopos keeps everything on the student's own computer, unlike most apps today, which are cloud subscriptions that keep your data on their servers. Students' study records sit close to health and medical information, and that kind of data should not be sent over the internet without their say. The data is stored in an encrypted database (SQLCipher). The app does not require an account, does not use cloud storage, and works fully offline. AI features are optional and use the student's own key, so data is shared only when they choose.

Migration to React

The original app had grown to about 30,000 lines of plain JavaScript and was getting risky to change. I moved it to React, starting from a full feature inventory so that every feature was kept, and old code was retired only after a script confirmed it was unused.

Single owners

Every rule lives in exactly one place. One module decides what is due for review, and the home screen, study sessions, flashcards and planner all read from it. When two screens work something out separately, they eventually disagree. One owner means one answer and one place to fix.

Headless logic

Scheduling, pacing and planning are pure functions that do not depend on the screen, the clock or storage. They can be tested thoroughly on their own and behave the same wherever they are used.

Clear state management

State is split into four layers: shared logic, encrypted study data, settings and background services. Each screen's state has exactly one owner in the store (Zustand), so any bug traces back to one place.

A plan recalculated from real progress

A saved study plan is out of date the moment a student misses a day. So the plan is not stored. It is recalculated from the student's real progress every time, and every change they make is applied the same way.

Locked-down desktop shell

In the Electron shell, the interface code is kept apart from the system and cannot load system modules. It reaches the system only through an approved list of channels, and every response is checked at that boundary.

The AI routerFour providers, the student's choices first, and failures that are always reported.

The app can work with four AI providers: Gemini, OpenAI, Anthropic and Groq. A router decides which model handles each task. I designed it around one principle: the student's choices always come first, and quality, capability and cost are weighed only within them.

  1. The student's choices

    A model the student has pinned is used as is. Otherwise the router stays within their chosen provider, their quality setting and their spending limit.

  2. What the task needs

    Each task declares what it requires, such as reading images, reading PDFs, structured output, long documents or keeping data on the computer. Models that cannot do the job are filtered out.

  3. Best fit, then cost

    Among the models left, it scores quality for that kind of work and moves up a tier only for harder material, such as difficult questions or answers that must be graded precisely.

  4. A plain message when not one model fits

    If not one of the available models meets every requirement, it uses the closest match and tells the student plainly, including what would fix it. It does not fail silently.

The routing decision is a pure function: the same inputs always give the same answer, without side effects, so every rule can be tested directly. Adding a new provider means registering it, not changing the router.

How it differs

Most study apps are tied to one cloud AI service and send everything to it. This router works across four providers, and it puts the student's choices and data rules ahead of the system's preferences.

How it was proved

Because each decision is a pure function, every rule (pins, capability filters, tier escalation, spending limits, the loud fallback) is checked directly by automated tests, without needing a live AI service.

The question generatorSeven stages, four rejection gates, benchmarked against 13 published and commercial systems.

The generator is a pipeline of seven stages, using several AI models and code checks, each with one job. Four of the stages can reject a question, and anything that fails is discarded rather than patched.

  1. Source first

    Every question starts from one section of a real text: OpenStax for the sciences, published works for reading passages.

  2. Blueprint

    The question is planned before it is written: the skill it tests, the reasoning it needs, and the specific mistake each wrong answer is built to catch.

  3. Write

    Passage, question, four options and a step-by-step explanation, written only from the source and the blueprint.

  4. Blind solve

    A separate model answers without seeing the key. If it does not reach the intended answer, the question is removed.

  5. Grounding check

    Every fact the answer depends on must be found in the source text. Anything unsupported is removed.

  6. Rules in code

    Fixed checks that a model cannot argue past: format, option letters, explanation steps, giveaway wording and duplicates.

  7. Measured against the exam

    Each batch's mix of skills and difficulty must sit within the real exam's range, and batches are rated blind alongside real exam questions.

How it differs

I benchmarked the design against 13 published and commercial systems. Research generators rely on templates built by experts or a human reviewer at the end, and commercial banks do not publish how their questions are made. A single AI prompt produces acceptable questions only 18 to 31 percent of the time in a published medical study. This pipeline does not have a human in the loop, so its gates are built to carry that load: every wrong answer is planned around a real mistake, and every fact is checked against the source.

How it was proved

Batches were rated blind, mixed in with official AAMC and commercial questions. On biology and biochemistry, its explanations scored 4.87 out of 5, against 4.10 for UWorld and 3.08 for the AAMC's own. Each round of testing fed the next version of the pipeline.

How it is testedSimulated students, the real app driven day by day, and signed proof that tests ran.

Simulated students

Simulated students study for a week, a month, a year and several years, on the real encrypted database. They miss days, move their exam date, import decks and rest, and the app is checked every simulated day. One run loads 100,000 cards to test scale.

The real app, day by day

Automated tests open the real desktop app and study through it for weeks at a time with a controlled clock, then compare the app's plan against an independent calculation every day.

Rules about the plan

Property tests state rules the planner must always keep, then check them across many randomly generated study histories with missed days, rest days and exam date changes.

Signed test records for finished tasks

A task can only be marked done with a signed record that its tests ran. The system re-runs that command itself, and blocks any commit made with code newer than the last passing test run.

Automated checks on app wording

The app's writing rules are checked automatically by the test suite: plain everyday words, without internal jargon, dashes or trailing dots. A screen that breaks them fails the tests.

Source and licence credits

Every textbook figure carries its source and licence on the card. A licence audit checked the terms shown across the app.

My role

I lead the product, which means I define the requirements and quality standards, design the interface, and test every release. My biochemistry degree lets me verify the science content directly.

I treat AI coding agents as capable but untrusted. They write fast, and they can also hallucinate, so their work is not trusted until a test proves it.

In early 2026, I ran ten agent sessions in parallel, on my desktop and on a linked laptop once the desktop's 32 GB of RAM ran out. They showed that throughput was not the bottleneck. The agents fell into retry loops on the same failure, without root-cause analysis, because they did not have a model of the system's architecture. I paused feature work and spent several months building the harness. It has deterministic gates on every change, working rules in a CLAUDE.md file that each agent loads at start, and all state kept in the repository rather than in any session. The plan, the decisions and the handoffs move between Claude and Codex accounts without loss. Feature work has run smoothly since.

Every task starts as a written contract, with a test designed to fail on bad work. The agents, Claude Code and OpenAI Codex, write code in isolated branches, and a second agent, blind to the first, tries to break the result. A change does not merge until the Node unit tests and the end-to-end tests pass again and leave a record that they ran. At the key gates, I run the app myself and sign off.
